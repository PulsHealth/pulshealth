PulsHealth is open source. You can use the iPhone app to inspect your Apple Health records, export them as files, or keep a database updated. You can also read the code and build your own tools on the same upload protocol.

The iPhone app, Swift sync library, reference server, protocol specification, dashboards, and this website are in [one Apache-2.0 repository](https://github.com/PulsHealth/pulshealth). You can inspect them, run the stack yourself, or build a receiver that accepts the documented format.

## Start with the data already on your phone

You do not need a server or a PulsHealth account to use Explore or Export in the [iPhone app](https://apps.apple.com/us/app/pulshealth/id6757657354).

**Explore** helps you understand what is in Apple Health. Open a data type to inspect its sample count, sources, value distribution, and how observations arrive over time. That answers a practical first question: do you have the measurements needed for the analysis you had in mind?

**Export** writes selected data to CSV, JSON, or JSONL files. Choose the types and date range for that export, then save or share the result. This works on demand without configuring sync. CSV is useful for a spreadsheet; JSONL retains the richer structured representation. Their differences are documented in the [export guide](/docs/export/).

Free includes full Explore, manual exports of all supported types from the last 30 days, and sync of up to five distinct types from the last 30 days. Pro unlocks all available history and unlimited sync types, subject to Health access. Self-hosting does not remove those app limits.

The 30-day limit concerns what the app reads. It does not delete older records already in your database; Free sync can keep adding new data to an existing history. App purchases and hosting are separate. [Current plans](/pricing/)

A file is enough for a one-off spreadsheet or chart. A database is useful when you want to repeat the analysis as new records arrive.

## Choose where ongoing sync goes

PulsHealth can send selected records to a database hosted for you or a database you operate. Both paths use the project's server software, but the responsibility for the stored data is different.

| Path | What you take on | Where your synced health data lives |
|---|---|---|
| Export a file | Decide where to save and share it | Your chosen file destination |
| Hosted PulsHealth database | Request access, connect your phone, choose what to sync | The PulsHealth operator's server |
| Self-hosted database | Run, secure, update, and back up the stack | Infrastructure you control |

Hosted access starts with an [access request](https://app.pulshealth.com/signup), subject to approval and availability. Once approved, connect from the app’s **Sync** tab, review the destination, then choose the types and history before applying the setup. The [desktop access guide](/blog/view-apple-health-on-mac-pc/) walks through the hosted connection. For your own server, follow the [pairing guide](/docs/setup/#4-pair-the-app-and-choose-what-to-sync). The [current App Store listing](https://apps.apple.com/us/app/pulshealth/id6757657354) describes both connection options.

For self-hosting, start with the [setup guide](/docs/setup/). The stack includes PostgreSQL with TimescaleDB, ingestion, a read API, a web viewer, Grafana, and the MCP integration. Installation commands and current requirements live in that guide.

## What happens after you connect a database

You choose the data types and the history you want to send. The app reads available records and keeps track of acknowledged uploads so interrupted work can resume. It also handles newly available records and supported deletions as syncing continues.

The database keeps individual measurements, sleep intervals, workouts, activity rings, and aggregate series distinct. The [database guide](/docs/database/) explains which to query, including how to avoid counting overlapping phone and Watch records twice.

Sync also depends on the phone. Health access, Watch-to-iPhone delivery, connectivity, and the execution time iOS grants all affect when a record arrives. A database makes data easier to use after it gets there; it does not make background delivery instantaneous. The app's status and activity views help you see progress and diagnose interruptions.

For self-hosting, backups require attention: the project provides an opt-in backup service, and it is your responsibility to enable and test it. A running database and a recoverable backup are separate achievements.

## Connect tools without replacing your data store

Once records arrive, you can browse them in the web viewer, query them with SQL, or use the read API and Grafana. Changing the presentation does not require another phone export.

The MCP server lets compatible AI assistants query the product API with read-only tools. It can support questions such as which days have missing records or how recorded workout frequency changed between two periods. Hosted connections use account authorization; self-hosted setups have their own configuration. The [AI connection guide](/docs/ai/) documents supported connection methods and the tested Claude flow.

Read-only access prevents the connector from changing stored records. It does **not** keep queried data away from the assistant's provider. Authorizing a connection allows that provider to receive what its assistant reads, under its own terms. Read the [privacy policy](/privacy/) before connecting, and check source records when an answer matters.

## A specified protocol gives you another option

You do not have to use the reference database. The [Puls Sync Protocol](/docs/protocol/) defines the upload format, with schemas and example fixtures. The repository includes a small Python receiver that writes to SQLite, showing how an independent implementation can work.

The protocol describes what a receiver must accept independently of the reference server’s implementation.

Start with Explore or a small export, then connect a database if you need ongoing access. For code, protocol fixtures, and contribution instructions, [visit the repository](https://github.com/PulsHealth/pulshealth). Bug reports are welcome in [GitHub issues](https://github.com/PulsHealth/pulshealth/issues); remove private records and credentials from examples before posting.
