Apple Health collects a useful history, but the next step often happens somewhere else: a spreadsheet, a browser dashboard, a Python notebook, or a question you want an assistant to help investigate. PulsHealth gives that history a route out of the phone, with choices about where it goes.

The iPhone app, Swift sync library, reference server, protocol specification, dashboards, and this website are in [one Apache-2.0 repository](https://github.com/PulsHealth/pulshealth). You can inspect them, run the stack yourself, or build a receiver that accepts the documented format.

## Start with the data already on your phone

You do not need a server or a PulsHealth account to start. The free [iPhone app](https://apps.apple.com/us/app/pulshealth/id6757657354) has two useful entry points before you connect a database.

**Explore** helps you understand what is in Apple Health. Open a data type to inspect its sample count, sources, value distribution, and how observations arrive over time. That answers a practical first question: do you have the measurements needed for the analysis you had in mind?

**Export** writes selected data to CSV or JSONL files. Choose the types and date range for that export, then save or share the result. This works on demand without configuring sync. CSV is useful for a spreadsheet; JSONL retains the richer structured representation. Their differences are documented in the [export guide](/docs/export/).

The distinction matters when you have a single task. If you want to make one chart from last month's measurements, a file may be all you need. A continuously updated database becomes useful when you want that chart to stay current, query a longer history repeatedly, or connect other tools.

## Choose where ongoing sync goes

PulsHealth can send selected records to a database hosted for you or a database you operate. Both paths use the project's server software, but the responsibility for the stored data is different.

| Path | What you take on | Where your synced health data lives |
|---|---|---|
| Export a file | Decide where to save and share it | Your chosen file destination |
| Hosted PulsHealth database | Request access, connect your phone, choose what to sync | The PulsHealth operator's server |
| Self-hosted database | Run, secure, update, and back up the stack | Infrastructure you control |

Hosted access currently starts with an [access request](https://app.pulshealth.com/signup). Submitting the form does not immediately create a working account: requests require approval. Once admitted, use your account page's pairing instructions to connect your iPhone. As of this update, the App Store version is **1.6**: use its existing database pairing flow. The newer in-app hosted sign-in flow is in the source repository but is not part of that shipped version. The [release record](https://github.com/PulsHealth/pulshealth/blob/main/docs/appstore/README.md#release-record) tracks the distinction.

For self-hosting, the [server guide](/docs/server/) covers the Docker Compose stack and phone connection. It includes PostgreSQL with TimescaleDB, ingestion, a read API, a web viewer, Grafana, and the MCP integration. Use the maintained guide for commands and current requirements rather than copying an old installation recipe from an announcement.

## What sync does—and what it cannot promise

You choose the data types and the history you want to send. The app reads available records and keeps track of acknowledged uploads so interrupted work can resume. It also handles newly available records and supported deletions as syncing continues.

There are different shapes of data. Individual measurements, sleep categories, workouts, daily activity summaries, and aggregate series are not interchangeable rows. PulsHealth preserves those distinctions so that an analysis can ask for the appropriate representation. The [database guide](/docs/database/) explains how to query them without silently double-counting overlapping sources or confusing summaries with raw records.

Sync also depends on the phone. Health access, Watch-to-iPhone delivery, connectivity, and the execution time iOS grants all affect when a record arrives. A database makes data easier to use after it gets there; it does not make background delivery instantaneous. The app's status and activity views help you see progress and diagnose interruptions.

For self-hosting, backups require attention: the project provides an opt-in backup service, and it is your responsibility to enable and test it. A running database and a recoverable backup are separate achievements.

## Connect tools without replacing your data store

The web viewer is one way to browse your records. SQL, downloadable files, the read API, and Grafana provide other routes. You can change the presentation without asking your phone to collect its history again.

The MCP server lets compatible AI assistants query the product API with read-only tools. It can support questions such as which days have missing records or how recorded workout frequency changed between two periods. Hosted connections use account authorization; self-hosted setups have their own configuration. The [AI connection guide](/docs/ai/) documents supported connection methods and the tested Claude flow.

Read-only access prevents the connector from changing stored records. It does **not** keep queried data away from the assistant's provider. Authorizing a connection allows that provider to receive what its assistant reads, under its own terms. Read the [privacy policy](/privacy/) before connecting, and check source records when an answer matters.

## A specified protocol gives you another option

You do not have to use the reference database. The [Puls Sync Protocol](/docs/protocol/) defines the upload format, with schemas and example fixtures. The repository includes a small Python receiver that writes to SQLite, showing how an independent implementation can work.

That is an important part of making the source useful. A receiver should be able to follow an explicit contract rather than reverse-engineer whichever server implementation happens to exist today.

If you want to try PulsHealth, begin with Explore or a small export. If you need ongoing access, choose a hosted account or follow the self-hosting guide. If something is unclear or broken, bring a reproducible example to [GitHub issues](https://github.com/PulsHealth/pulshealth/issues), with private records and credentials removed. Useful health-data tools begin with understanding what the data actually says.
